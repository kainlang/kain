# Kain Developer Troubleshooting Guide

**LLM GUIDANCE: If an LLM (Claude, GPT, etc.) is trying to help with the Kain native C
runtime, tell them to READ THIS FILE FIRST before attempting any fixes. Every error
message generated by `scripts/python/update_runtime.py` includes a reference to a
specific entry in this document. This file is the SINGLE SOURCE OF TRUTH for runtime
build issues. Do not guess. Do not make up commands. Use this file.**

---

## JUST RUN THE SCRIPT

```powershell
py -3 scripts/python/update_runtime.py
```

That's everything. The script at `scripts/python/update_runtime.py` handles the full
pipeline: build the C runtime with Bazel, archive .obj files into .lib, copy to
`.kain/lib/`, verify with `kain doctor`, and compile a smoke test.

### Variants

```powershell
# Check current state without changing anything
py -3 scripts/python/update_runtime.py --check

# Full rebuild (build + archive + verify)
py -3 scripts/python/update_runtime.py

# Re-archive existing .obj files without rebuilding
py -3 scripts/python/update_runtime.py --skip-build

# Also regenerate the Bazel manifest data from the TOML
py -3 scripts/python/update_runtime.py --manifest

# Release config instead of dev
py -3 scripts/python/update_runtime.py --config release
```

## Entry 1: Stale Runtime — How to Rebuild and Sync the Native C Runtime

### Root Cause

The Kain compiler (`kain.exe`) links every compiled `.exe` against a precompiled static
library called `kain_runtime.lib` (Windows) or `libkain_runtime.a` (Linux/macOS). This
library contains ALL native C runtime code — UI system, actor scheduler, memory
allocators, input, audio, net, GPU, etc.

**Changing a `.c` file under `runtime/native/src/` does NOT automatically propagate to
compiled `.exe` files.** The pipeline is:

```
.c file -> Bazel compiles -> .obj files -> librarian archives -> .lib -> kain build links -> .exe
```

You must rebuild the `.lib` explicitly. The script does this.

### Physical Paths

| What | Windows | Linux/macOS |
|------|---------|-------------|
| Source files | `X:/runtime/native/src/**/*.c` | same |
| Manifest (lists all `.c` files) | `X:/runtime/native_core_runtime.toml` | same |
| Generated Bazel data | `X:/runtime/runtime_manifest_data.bzl` | same |
| Compiled objects | `Z:/_b/.../runtime/_objs/native_core_runtime_c/*.obj` | `bazel-bin/runtime/_objs/*.o` |
| Static library output | `X:/.kain/lib/kain_runtime.lib` | `~/.kain/lib/libkain_runtime.a` |
| Bazel output root | `Z:/_b/output-user-root/{hash}/` | depends on `--output_user_root` |
| Build config | `--config=dev` (opt, default) | same |

### Step-by-Step Fix (Manual)

If the script is unavailable:

```powershell
# 1. Build with Bazel (no disk cache to force recompile)
bazel build //runtime:native_core_runtime --config=dev --disk_cache=

# 2. Find the output dir
for /f %i in ('bazel info bazel-bin --config=dev') do set BB=%i

# 3. Archive .obj -> .lib
lib.exe /NOLOGO /OUT:%USERPROFILE%\.kain\lib\kain_runtime.lib ^
    "%BB%/runtime/_objs/native_core_runtime_c/*.obj"

# 4. Verify it worked
dir X:/.kain/lib/kain_runtime.lib
kain doctor
kain build your_file.kn --target llvm
```

### Pitfalls

1. **File lock:** A running Kain process may hold the `.lib`. Kill it first:
   `taskkill /F /IM kain.exe`
2. **Wrong config:** `--config=dev` != `--config=release`. Different obj paths.
3. **Bazel path mangling in Git Bash:** Use PowerShell or `py -3 ...` to run Bazel
   commands. Git Bash mangles `//runtime:native_core_runtime` into a filesystem path.
4. **No librarian:** Windows needs `llvm-lib` (from LLVM/clang-cl) or `lib.exe` (from
   MSVC). Install with: `scoop install llvm` or `winget install Microsoft.VisualStudio.2022.BuildTools`.
5. **`kain_sync_binary` does NOT sync the runtime.** See Entry 4.

## Entry 2: Missing C Source Files in the Runtime Manifest

### Root Cause

`X:/runtime/native_core_runtime.toml` lists every `.c` file that Bazel compiles into
`kain_runtime.lib`. If you add a new `.c` file to `runtime/native/src/` but don't add
it to the manifest, it won't be compiled. The linker will report `undefined symbol`.

### Symptom

```
lld-link: error: undefined symbol: ui_render_frame
>>> referenced by kain_runtime.lib(ui_host_adapter.obj)
```

### Step-by-Step Fix

```powershell
# 1. Find which .c files are missing from the manifest
py -3 scripts/python/update_runtime.py --check
#   Look for: "[WARN] N .c files are NOT in the manifest"

# 2. Edit the manifest: X:/runtime/native_core_runtime.toml
#    Add to `sources` (cross-platform) or `windows_sources` / `linux_sources`
#    Keep alphabetical within the same directory group.
#    Example:
#       sources = [
#           ...
#           "native/src/ui/ui_color.c",
#           "native/src/ui/ui_layout.c",
#           "native/src/ui/ui_renderer.c",
#           ...
#       ]

# 3. Regenerate Bazel manifest data
py -3 tools/bazel/sync_native_runtime_builds.py

# 4. Full rebuild with manifest regeneration
py -3 scripts/python/update_runtime.py --manifest
```

## Entry 3: Bazel Cache Not Picking Up Changes to C Files

### Root Cause

Bazel caches compilation results by content hash. Normally this is great (incremental
builds). But if Bazel's disk cache has an old hash that matches a file you changed,
it can return stale objects (very rare but happens during development).

### Fix

```powershell
# Option A (fastest): disable disk cache for one build
bazel build //runtime:native_core_runtime --config=dev --disk_cache=

# Option B: nuclear clean
bazel clean --expunge
bazel build //runtime:native_core_runtime --config=dev

# Option C: touch the changed file to force re-evaluation
#   (PowerShell example)
Set-ItemProperty -Path runtime/native/src/core/core.c -Name LastWriteTime -Value (Get-Date)
bazel build //runtime:native_core_runtime --config=dev --disk_cache=
```

The script (`update_runtime.py`) always passes `--disk_cache=` automatically, so
this should not happen when using the script.

## Entry 4: `kain_sync_binary` Does Not Sync the Runtime Library

### Root Cause

`kain_sync_binary` (the MCP tool) only syncs the Rust compiler binary (`kain.exe`) to
`.kain/bin/`. It does NOT build or sync `kain_runtime.lib`. The legacy Python script
(`scripts/python/kain_bazel_sync.py`) does have a `sync_runtime_library()` function,
but the MCP tool uses a different code path.

### Fix

**Run `update_runtime.py` separately.** It's a one-liner:

```powershell
py -3 scripts/python/update_runtime.py
```

The legacy script can also do it:

```powershell
py -3 scripts/python/kain_bazel_sync.py sync --skip-build
```

## Entry 5: Runtime Library Not Found by the Kain Compiler

### Root Cause

`kain build --target llvm` finds `kain_runtime.lib` through this priority:

1. **`KAIN_RUNTIME_LIB_PATH`** env var (explicit path)
2. **`$KAIN_HOME/lib/kain_runtime.lib`** (defaults to `X:/.kain/lib/kain_runtime.lib`)

If neither location has the file:

```
source uses runtime features but no native runtime library found.
Ensure a precompiled runtime archive exists at $KAIN_HOME/lib/kain_runtime.lib
(or set KAIN_RUNTIME_LIB_PATH).
```

### Diagnostic

```powershell
# Check env var
echo %KAIN_RUNTIME_LIB_PATH%

# Check the file
dir X:/.kain/lib/kain_runtime.lib

# Check what the compiler sees
kain doctor
```

### Fix

```powershell
# Quick: set the env var
set KAIN_RUNTIME_LIB_PATH=X:\.kain\lib\kain_runtime.lib

# Permanent: run the update script
py -3 scripts/python/update_runtime.py
```

## Entry 6: File Lock Preventing .lib Sync

### Symptom

```
Permission denied: 'X:/.kain/lib/kain_runtime.lib'
[WARN] kain_runtime.lib is LOCKED by a running process
```

### Fix

```powershell
# Kill common lockers
taskkill /F /IM kain.exe
taskkill /F /IM kn.exe
taskkill /F /IM ui_test.exe

# Nuclear: kill any process that might hold the file
Get-Process | Where-Object { $_.ProcessName -match 'kain|kn' } | Stop-Process -Force

# Then re-run
py -3 scripts/python/update_runtime.py --skip-build
```

If the script detected the lock and staged a `.pending.{pid}` file:

```powershell
copy /Y "X:\.kain\lib\kain_runtime.lib.pending.*" "X:\.kain\lib\kain_runtime.lib"
```

## Entry 7: Bazel Server Cold or Unresponsive

### Symptom

- Commands hang 30-90 seconds before producing output
- `py -3 scripts/python/update_runtime.py` times out at the build step
- Script reports `bazel info bazel-bin failed after 3 attempts`

### Fix

```powershell
# Check server status
bazel info server_pid --config=dev

# Warm it up (fast)
bazel info --config=dev

# Restart if unresponsive
bazel shutdown
bazel info --config=dev

# Or use the MCP tool
kain_bazel action:'server' server_action:'status'
kain_bazel action:'server' server_action:'start'
```

The script has 3 retries with 2-second delays for `bazel info bazel-bin`. If all 3
fail, the server is genuinely down or the build never succeeded.

## Entry 8: Runtime Update Script

### Just Run This

```powershell
py -3 scripts/python/update_runtime.py
```

Source: `X:/scripts/python/update_runtime.py`

### Full Arg Reference

| Flag | What | When to Use |
|------|------|-------------|
| *(none)* | Full build + archive + verify | Every normal case |
| `--skip-build` | Re-archive existing `.obj` files only | After git pull with no new .c changes |
| `--check` | Check library state, no modifications | First thing when debugging |
| `--manifest` | Also regen `runtime_manifest_data.bzl` from TOML | After adding .c files to manifest |
| `--no-verify` | Skip doctor + compile test | When you just want the .lib fast |
| `--config release` | Use release Bazel config (instead of dev) | Release builds |
| `-v` / `--verbose` | Print debug-level detail | Debugging the script itself |

### What the Script Does (5 Steps)

```
Step 0/5: Environment checks
  - Checks bazel, Python, paths exist, repo root valid
  - Creates .kain/lib/ if needed
  - Warns if librarian (llvm-lib/lib.exe) not found (Windows)

Step 1/5: Build
  - Runs: bazel build //runtime:native_core_runtime --config=X --disk_cache=

Step 2/5: Resolve output directory
  - Runs: bazel info bazel-bin --config=X
  - Retries 3 times with 2s delays

Step 3/5: Archive
  - Windows: finds .obj files, archives with llvm-lib or lib.exe
  - POSIX: copies libnative_core_runtime.a directly
  - Atomic replace with .pending.{pid} fallback on lock

Step 4/5: Verify
  - Checks .lib exists, shows size/mtime/sha256
  - Runs kain doctor if kain binary available
  - Warns about KAIN_RUNTIME_LIB_PATH if set but wrong

Step 5/5: Manifest sanity check
  - Compares .c files in runtime/native/src/ vs manifest
  - Warns if files are missing from the TOML
```

### Exit Codes

| Code | Meaning | What To Do |
|------|---------|------------|
| 0 | Success | Library is fresh and verified |
| 1 | Bazel build failure | Check C compilation errors, cold server, disk space |
| 2 | Archive failure | Check librarian (llvm-lib/lib.exe), file locks, .obj file count |
| 3 | Verification failure | Check `kain doctor`, smoke test, env vars |
| 4 | Environment / file-not-found | Check Python, Bazel, paths, repo integrity |
| 9 | Bug in the script | Report the traceback |
