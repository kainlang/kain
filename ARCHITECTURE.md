# Kain Architecture

This file is the durable repo overview for the current Kain checkout.
It is the fast way for future agents to understand what Kain is, where the important code lives, and which architectural rules matter enough to preserve.

## Documentation System

The repo's documentation is deliberately split by trust level and reader intent:

- `guides/` is the canonical long-form guide tree for the live checkout.
- `guides/reference/legacy-crosswalk.md` translates stale prose and old folder names into the current guide tree.
- `guides/pipelines/` holds the conceptual Omni and Fabric orchestration pages.
- `guides/ue5/` holds the conceptual Unreal-facing authoring and packaging pages.
- `docs/` is legacy support material and may lag behind the code; do not promote it back to the source of truth.
- `docs/examples/` is the deliberate exception inside `docs/`: it is now a runnable, manifest-driven Kain source suite with real `.kn` files plus a validator, and it exists to give agents a locally proven authoring ladder.

When the docs and code disagree, treat the mismatch as a signal to update the canonical guide tree from source rather than to copy the stale wording forward.

## What Kain Is

Kain is a compiled multi-target language toolchain, an executable semantic runtime, and an embeddable host stack.

It is not only a `KAIN.toml`/materialization language or an orchestration shell over Rust, C, Python, Node, and GPU targets. `crates/kain-core` already owns real language execution for substantial parts of Kain itself: parsing, `comptime`, executable-body typechecking, direct interpretation of functions and blocks, closures, control flow, `match`, async/await, actor runtime execution, JSX/UI expression evaluation, and runtime execution of compiler-owned declarations such as `patch`, `converge`, `world`, `entangle`, `orchestrate`, `axiom`, `pulse`, `shatter`, and `teleport`. Shared actor vocabulary now lives in `crates/kain-actor` so supervision, mailboxes, scheduler policy, behavior contracts, native ABI descriptors, and typed actor contracts have a dedicated crate instead of hiding only inside `kain-core`. Portable filesystem semantics now live in `crates/kain-fs`, with `kain-core`, the root `stdlib/` modules, LLVM, and direct C consuming the same typed file/path contract instead of each lane inventing its own ad hoc file helpers. Typed input semantics now live in `crates/kain-input`, so human, CLI, UI-runtime, native-platform, synthetic, and agent/LLM intent input reduce through the same frames, actions, axes, text commits, and replay traces instead of target adapters inventing their own event models. Portable networking contracts now live in `crates/kain-net`, with the raw native substrate in `stdlib/net.kn`, public aliases at `std.net` / `std.http` / `std.tls` / `std.http2`, and `runtime/native/include/net_system.h` exposing TCP, protocol-aware HTTP request/response metadata, capability queries, Windows-first HTTPS client flows, and early HTTP/2 client negotiation primitives to LLVM/direct-C Kain builds. Portable child-process and PTY contracts now live in `crates/kain-process`, with `stdlib/process.kn` and `runtime/native/include/process_system.h` exposing the same handle-driven process model to LLVM/direct-C Kain builds. The immediate execution loop now lives in `crates/kain-run`, which resolves Kain source, C files, Cargo crates, Fabric manifests, Node/Bun entries, blades, and workspace `[run]` metadata through one reportable pipeline instead of scattering `run` behavior through CLI branches.

The build, packaging, and adapter crates matter because Kain is meant to ship into multiple targets, not because the language is limited to manifests and glue. The durable architecture rule is: keep authored logic in Kain when it belongs to Kain semantics, and use host bridges when the capability is genuinely platform-, ABI-, or ecosystem-owned.

Stdlib authoring rule: prefer public root-domain imports such as `std.actor`, `std.fs`, `std.http`, `std.process`, `std.graphics`, `std.ui`, `std.text`, `std.collections`, `std.crypto`, `std.alloc`, `std.build`, `std.proof`, `std.bench`, `std.attrition`, and `std.certify` in new Kain source. The root `stdlib/` folder is now the single canonical authored surface for those domains, LLVM/direct-C loads that same root profile directly, and the older `std.native.*` path is compatibility-only when an old file still mentions it.

Stdlib inspectability rule: `kain stdlib-map` is the canonical generated atlas for agents and tools that need the native LLVM stdlib in one scan. It writes `stdlib/stdlib.map.json` plus compact `stdlib/STDLIB_MAP.llm.md`, indexes only top-level `stdlib/*.kn` root-domain modules, merges Rust-registered builtins and native runtime service manifests, and is guarded by `//stdlib:stdlib_map_check` so native stdlib edits cannot silently drift the atlas. Target/vendor overlays such as `stdlib/ue5`, `stdlib/python`, `stdlib/javascript`, `stdlib/interop`, and `stdlib/c` are intentionally out of this atlas.

Platform package rule: native dynamic libraries enter through a deterministic lock/import lane, not public generic ABI call magic. `runtime/native` owns only `platform.library` open/resolve/close and target capability reporting; `crates/kain-c-ffi` owns `kain import platform`, target-aware lockfiles under `.kain/platform/<package>/<target-triple>/`, generated typed thunks, relocatable package metadata, stable blocked-symbol reasons, and package-specific metadata such as Vulkan loader dispatch. `build.kn` / `platform.kn` may declare graph requirements like `platform_requirement("vulkan").provider("system")` or legacy `platform_package("vulkan").provider("system")`, equivalent `KAIN.toml` data should produce the same graph, and any override must be explicit in provenance instead of hiding filesystem/env decisions. `crates/kain-run` consumes that provenance in plan/report output, stages package locks before execution, adds generated platform modules and reports to watch inputs, and exposes `KAIN_PLATFORM_LOCKS` / `KAIN_PLATFORM_GENERATED_ROOTS` to process-backed run units.

Build authority rule: `build.kn` is now the preferred blade/workspace authority surface, not just an optional task sidecar. `crates/kain-blades` synthesizes an effective manifest by overlaying script-authored `workspace_defaults()`, `package("...")`, `blade("...")`, `build_defaults()`, `run_defaults()`, and first-class `std::build`/`std::test`/`std::proof`/`std::bench`/`std::attrition`/`std::certify` task constructors onto compatibility `KAIN.toml`. Script-only blades and workspaces may omit `KAIN.toml` for root metadata, blade discovery, build defaults, run defaults, and explicit build tasks, while `KAIN.toml` remains a supported compatibility/default lane and still carries surfaces such as current C FFI metadata that have not been promoted into the script vocabulary yet.

Blade dependency rule: a library blade may own `[c_ffi]` bridge requirements. `crates/kain-blades` resolves C FFI libraries transitively through blade dependencies, while the final `kain-run` executable unit owns materializing the inherited headers, sources, shared libraries, include paths, and `KAIN_TRANSITIVE_C_FFI_*` provenance. New blade module trees should not require hand-listing every nested folder: explicit `source_roots` remain the source roots, but module roots are inferred from nested `.kn` files and generated platform modules under `.kain/platform`.

Converge backend rule: `converge` remains the semantic selector/validator, not a hardcoded SIMD switch. Native LLVM now carries multiple fast lanes, static lanes collapse directly, and CPU-gated lanes route through the native CPU capability plus converge selector/cache services. Real AVX2/AVX-512 acceleration should enter first as FFI-backed or runtime C kernels, then be proved equivalent to the spec lane and benchmarked through the existing harness. The native SIMD kernels live at `runtime/native/src/core/simd.c` with root stdlib wrappers in `stdlib/runtime.kn`; the current lane includes direct dot kernels plus the proof-backed affine fill/repeated-dot accumulator used by `benchmark/cases/simd_lane_mix`.

Important language-wide rule: native/Rust/C code provides capabilities, ABI substrate, validation, diagnostics, and target integration. Kain source authors behavior, engines, scenes, UI structures, primitives, simulation loops, and workflows. Do not add host-side catalogs, templates, default scenes, built-in primitives, or product layouts when a generic capability surface would let Kain author the system directly.

The repo currently spans five connected layers:

1. `crates/kain-core`
Language semantics, parsing, typing, effects, comptime, interpreter lanes, runtime-contract emission, shader metadata, and other compiler-owned truth.

2. Materialization, import, build, and capsule orchestration
`crates/kain-driver`, `crates/kain-omni`, `crates/kain-selfhost`, `crates/kain-build`, `crates/kain-run`, `crates/kain-amalgamate`, and importer crates turn Kain semantic truth into emitted bundles, packaged artifacts, portable source capsules, immediate execution plans, imported surfaces, and multi-runtime workflows.

3. Runtime and host bridges
`runtime/native` is the canonical ABI floor and C runtime substrate. `crates/kain-host`, `crates/kain-sdk`, `crates/kain-reflect`, `crates/kain-foreign-abi`, `crates/kain-c-ffi`, `crates/kain-crate-ffi`, `crates/kain-python`, `crates/kain-node`, `crates/kain-codebase`, and `crates/kain-interop` provide host/runtime integration.

4. UI, native desktop, and 3D
`crates/kain-ui`, `crates/kain-ui-native`, and `crates/kain-3D` are the semantic UI and accelerated native presentation stack. The low-level single-file LLVM UI lane lives at the C ABI floor in `runtime/native/include/ui_system.h` and `runtime/native/src/ui/ui_system.c`: it exposes sessions, host frame presentation metadata, arbitrary authored node kinds, stable node keys, rects, styles, accessibility labels, text/font/resource handles, clipboard/IME/drag/menu/dialog state, events, hit testing, focus, dirty tracking, hot reload generations, and draw-command buffers without a host-owned component catalog. The compiled-bundle/runtime reload lane now sits beside it in `runtime/native/include/ui_runtime.h`, `runtime/native/include/ui_hot_reload.h`, `runtime/native/src/ui/ui_runtime.c`, and `runtime/native/src/ui/ui_hot_reload.c`: bundle reload/state transfer is cross-platform by API, file-watch live reload works everywhere the runtime can stat the bundle path, and the shared-memory control ring is hidden behind platform-specific backends instead of being baked into the UI architecture. The low-level native graphics lane lives at `runtime/native/include/graphics_system.h` and `runtime/native/src/core/graphics_system.c`: it exposes sessions, backend targets, SPIR-V module registration, authored buffers, meshes, pipelines, frame submission, draw-command inspection, and diagnostics without a host-owned scene or primitive catalog.

5. Target adapters
`crates/kain-web`, `crates/kain-wasm`, `crates/kain-script`, `crates/gpu`, `crates/kain-gpu-runtime`, and the `crates/ue5*` family consume compiler-owned contracts for specific runtime environments.

## Non-Negotiable Ownership

- `crates/kain-core` owns language meaning, typed metadata, executable semantics, capability requirements, and shader/compute-plan semantics. The current keyword surface includes machine axioms (`axiom`), temporal beats (`pulse`), silicon-oriented layout intent (`shatter struct`), and destructive cross-world ownership handoff (`teleport`) beside the earlier compiler-owned intent keywords.
- `crates/kain-actor` owns reusable actor-system model types: actor IDs, addresses, message contracts, mailbox policy, lifecycle/supervision metadata, scheduler policy, behavior contracts, native ABI descriptors, registry snapshots, actor-system validation, and the typed actor contract consumed by `kain-core`.
- `crates/kain-ownership` owns the portable ownership-state memory model behind the first-class `collapse`, `observe`, and `decay` keywords: region kinds, legal state transitions, conservative world/entangle policy, imported-pointer borrow policy, lowering hints, and the `memory.ownership` capability name.
- `crates/kain-fs` owns portable filesystem semantics: path normalization, text/byte file operations, metadata and directory-entry shapes, temp paths, atomic writes, copy/move/remove behavior, sandbox/capability policy, `fs://` virtual roots, chunked/ranged IO, polling watchers, transactional filesystem journals, and typed filesystem errors shared by interpreter and native-facing stdlib code.
- `crates/kain-input` owns portable input semantics: source provenance, event shapes, data-driven action/axis bindings, frame reduction, text commits, agent intent events, deterministic traces, and replay. Host adapters translate raw OS/web/UE/UI/CLI events into this model; they do not define app-facing input policy.
- `crates/kain-net` owns portable networking contracts: TCP endpoints, HTTP request/response specs, HTTP protocol preferences, TLS client specs, capability-state descriptors, headers, route specs, listener/server/client handles, lifecycle state, and typed network errors. Native adapters implement these semantics; actor and entangle integrations layer above the transport instead of redefining sockets.
- `crates/kain-process` owns portable child-process and PTY contracts: process specs, stdio policy, cwd/env overrides, process/PTY handles, lifecycle state, and captured output shapes. Native adapters implement these semantics; they do not redefine process policy per host.
- `crates/kain-run` owns the operator-facing run pipeline: target inference, `[run]` manifest metadata, blade/workspace resolution, cached C/Cargo execution, dev/watch polling, process-backed reports, and `.kain/cache/run` / `.kain/reports/run` layout. CLI commands call this crate instead of implementing run behavior inline.
- `crates/kain-stdlib-map` owns the generated stdlib atlas consumed by agents, docs, and build checks. It must stay deterministic across Cargo and Bazel execution roots; parser fallback diagnostics are repo-relative for that reason.
- `crates/kain-amalgamate` owns the portable capsule lane: comment-safe `.kn` capsule formats, generated preview headers, `//!kain-capsule` metadata blocks, editable inline file sections, sealed archive payload validation, pack/inspect/unpack/materialize behavior, and digest-scoped `.kain/cache/amalgamate/<digest>/workspace` extraction. CLI `run`, `build`, and `check` should treat capsule inputs as a transparent bridge back into the normal blade/workspace pipelines.
- `crates/kain-foreign-abi` owns the shared foreign ABI type graph, scalar type table, pointer/callback/aggregate bridge classification, ownership-policy tags for imported raw pointers, and the durable proof pack for ABI arithmetic. Import lanes such as `kain-c-ffi` consume this crate instead of hardcoding incompatible scalar or pointer policy locally.
- `crates/kain-driver` owns emitted bundle truth and app/runtime materialization.
- `runtime/native` owns the stable ABI floor, startup, service contracts, and low-level host/runtime substrate. `runtime/blades` is the Kain-authored runtime-policy workspace above that floor: Kain source can own batching, scheduling posture, service composition, probes, and future runtime self-host lanes while C continues to expose raw OS/syscall/handle contact through coarse ABI boundaries. Native startup now lazily boots the pooled actor scheduler on first actor use instead of eagerly paying that cost for every pure compute executable. It also owns truthful CPU feature discovery and the process-local converge selector/cache/telemetry substrate used by native LLVM fast-lane dispatch.
- Native UI primitives are ABI substrate, not product UI. The runtime may expose generic handles and buffers, but buttons, panels, inspectors, viewports, shells, and catalogs must be authored in Kain source or `stdlib/`, not hardcoded as Rust/C host recipes.
- Native graphics primitives are ABI substrate, not a game engine or DCC catalog. The runtime may expose sessions, buffers, shader modules, pipeline handles, draw commands, and backend probes; scenes, meshes, primitive recipes, simulation loops, renderers, editors, and engine policy must be authored in Kain source or data.
- Host bridges and adapters extend Kain into external ecosystems; they do not downgrade Kain source into "configuration only."
- Accelerated Rust lanes may optimize execution, but they must consume the same compiler-owned bundles rather than inventing a second semantic model.
- Web, UE5, selfhost, and future lanes are adapters, not alternate definitions of what Kain source means.

## Actor Runtime Shape

- The native actor ABI lives at `runtime/native/include/actor.h` with implementation in `runtime/native/src/core/actor.c`. ABI v3 separates compatibility blocking actors from LLVM-native microcell actors: generated actors use `KAIN_ACTOR_ENTRY_KIND_MICROCELL_TURN`, `KainActorTurnFn(actor_id, mailbox, user_data, budget)`, and a default 64-message turn budget.
- LLVM actor lowering must emit nonblocking turn handlers that poll `kain_actor_try_receive` and return `KAIN_ACTOR_TURN_IDLE` or `KAIN_ACTOR_TURN_YIELDED`; it must not put generated actors back on blocking `kain_actor_receive` loops inside pooled scheduler workers.
- `kain_actor_send` appends to the mailbox under the mailbox lock and calls `kain_scheduler_ready_actor`. `kain_actor_ask_send_ref` is the ask-only exact-ref fast path: when the target is a local `MICROCELL` turn actor with an empty mailbox and no scheduler ownership bits set, it claims `in_scheduler_turn` inline on the caller thread instead of queueing a worker wakeup; otherwise it falls back to the normal mailbox path. Keep this mailbox->scheduler lock order intact so sends racing with a running turn cannot strand live mailbox messages.
- `in_scheduler_turn` now means a scheduler-owned microcell turn is in flight, whether that owner is a pooled worker or the local ask inline handoff. `kain_actor_execute_microcell_turn` and `kain_scheduler_finish_turn` are the shared turn/cleanup path; finish-turn clears the ownership bit and requeues iff mailbox work remains.
- TLS reply ports are synthetic actor refs backed by a reusable actor-table slot. Successful asks rearm the slot by bumping generation in place, so late stale replies fail the exact ref match while hot roundtrips avoid table remove/insert churn.
- Reply waits use a bounded spin window before falling through to the OS event/condition wait. Timeout-zero waits remain poll-like; nonzero waits may catch same-core actor replies without a kernel transition.
- Mailboxes cache only message nodes, not payload buffers, and the cache is capped per mailbox. Do not add payload caches unless a benchmark beats the generic malloc/copy path on the real actor row; the last attempted payload cache regressed.
- Legacy bootstrap actors intentionally run on direct compatibility threads now, and runtime shutdown joins those direct threads before actor-table cleanup. The pooled scheduler is for bounded microcell turns, and blocking legacy code must not be allowed to consume the worker pool used by native ask/reply traffic.

## Primary Data Flows

### Semantic execution flow

`Kain source -> lexer/parser -> comptime -> executable-body typecheck -> kain-core runtime/interpreter executes authored Kain logic`

This repo does not only compile source outward into foreign runtimes. `kain-core` is already an execution engine for meaningful language behavior:

- direct evaluation of functions, blocks, loops, assignment, field/index mutation, closures, and pattern matching
- async/await and future/poll semantics in the in-language runtime lane
- actor state initialization, message handling, runtime-side actor behavior, and `kain-actor` typed actor contract construction/validation
- JSX/UI expression evaluation and signal-driven UI contract execution
- runtime execution of `law`, `patch`, `converge`, `entangle`, and `orchestrate`, including law calls, converge verification, entangled state propagation, and patch transaction recording

When `kain run` succeeds, Kain is not merely validating authored source before handing work to another backend. In many cases it is executing the language's own semantic model directly. Treat that lane as a first-class truth source for what Kain code means.

### Compile and runtime bundle flow

`Kain source -> kain-core semantic analysis -> runtime contract / realtime app bundle / shader bundle metadata -> kain-driver materialization -> runtime/native and accelerated lanes consume the same bundle family`

The semantic-analysis part of that pipeline now includes real executable-body checks in `kain-core`, not only declaration registration. The compiler validates return values, call arguments, `match` arm type agreement, duplicate boolean arms, and `await` / `async` future typing before downstream codegen and bundle emission consume the typed program. That typechecked program also feeds the runtime/interpreter lane; bundle/codegen flows are downstream consumers of the same semantic truth, not a replacement for it.

That same frontend lane now owns six compiler-owned intent declarations:

- `law` lowers to callable invariant metadata through explicit `laws[]` contract sections, and the LLVM/C backends now emit laws as callable native-target functions.
- `patch` lowers to transactional mutation metadata with inferred undo mode plus explicit `patches[]` contract sections.
- `converge` lowers to dispatcher-plus-lane metadata with deterministic selection and executable `verify random(n)` verification through `converges[]`. Native LLVM now emits every eligible fast lane up to the backend cap, collapses purely static lanes directly, and routes CPU-gated lane sets through the native CPU/converge selector service.
- `world` lowers to shared state/surface projection metadata through sparse `worlds[]` entries and compiler-owned active-world selection.
- `entangle` lowers to single-writer state-coupling metadata through `entanglements[]` and the `state.entangle` capability; v1 interpreter semantics propagate authority endpoint writes to mirrors and reject direct mirror writes. The LLVM lane emits `@__kain_register_entanglements` calls into the native C runtime registry, and the direct C backend now emits a static metadata table plus a generated `__kain_register_entanglements()` thunk called from `main`.
- `orchestrate` lowers to strict typed stage metadata through `orchestrations[]`.

The runtime-contract and realtime-bundle families now both carry these explicit sections, and downstream adapters should consume them directly instead of reverse-engineering equivalent intent from local conventions.

Native target codegen for compiler-owned intents and filesystem calls is intentionally explicit:
`crates/kain-sys-codegen/src/codegen_llvm/mod.rs` owns LLVM lowering for semantic `Option`, `Result`, `Future`, `async` / `await`, `?`, `patch`, `law`, `converge`, `world`, `entangle`, `orchestrate`, `axiom`, `pulse`, `shatter`, `teleport`, and native stdlib wrapper signatures; `crates/kain-sys-codegen/src/codegen_c.rs` owns the experimental direct C source lane including string equality lowering for stdlib helper checks; `runtime/native/include/entangle.h` plus `runtime/native/src/core/entangle.c` provide the low-level C ABI registry; `runtime/native/include/machine_stones.h` plus `runtime/native/src/core/machine_stones.c` provide the machine-stones ABI; and `runtime/native/include/stdlib_abi.h` plus `runtime/native/src/core/stdlib_abi.c` provide the stdlib-facing C ABI facade consumed by LLVM/direct-C native builds.

### Networking Flow

`Kain std.net/std.http/std.tls/std.http2 -> stdlib/net/http/tls/http2 wrappers -> kain-net portable contracts -> runtime/native C net ABI -> raw sockets or platform HTTPS backend -> LLVM/direct-C executables`

The root `std.*` networking modules intentionally mirror the native profile so authored Kain code can treat networking as a built-in domain instead of a package hunt. `std.net` carries the raw TCP and shared HTTP handle surface, `std.http` carries the higher-level request/server helpers, `std.tls` carries the secure-client capability and HTTPS entrypoints, and `std.http2` carries protocol-selection intent plus negotiated-response inspection.

Two current runtime rules matter:

- Incoming server request handles are auto-released after `http_respond_*`, which fixes the earlier repeated-local-POST capacity failure and means request-slot reuse is now part of the durable conformance story.
- HTTP/2 is still an early client-side lane. The request can express `http/2`, capability state is queryable, and the secure WinHTTP path can report the negotiated response protocol; do not assume a full portable HTTP/2 session/runtime yet.

The LLVM native lane represents `Option<T>`, `Result<Ok, Err>`, and `Future<T>` as native tagged `i8*` handles at the ABI boundary rather than erasing them to their payload type. The C facade exposes constructors, tag checks, payload-copy helpers, ready-future/await helpers, and intent counters. This is the compatibility layer until the backend grows fully typed aggregate payloads for every `T`; for now, generated payload extraction is strongest for scalar payloads and focused fixture coverage.

LLVM ownership semantics now split one important fast path: ordinary non-extern RC parameters still behave as owned locals that release on scope exit, but authored non-extern `String` parameters are lowered as borrowed aliases when the frontend knows the callee signature. `crates/kain-sys-codegen/src/codegen_llvm/mod.rs` caches `strlen` once per borrowed string param at function entry, skips caller-side retain for those direct calls, and marks the callee local as borrowed so scope exit does not release it. Keep caller/callee coordination together: if the borrowed-string parameter mask or borrowed-local mark drifts, the string hot path either regresses back into retain/release ping-pong or reintroduces heap corruption.

LLVM ownership lowering also has a new compiler-owned `EphemeralLocal` provenance lane for fresh single-cell helper allocations that never escape their local ownership trace. When `crates/kain-sys-codegen/src/codegen_llvm/mod.rs` can prove the cell is only used through a balanced local `collapse` / `observe` / `decay` sequence, it materializes stack-backed byte storage, erases `__kain_alloc` plus ownership runtime calls, and lowers `mem_load` / `mem_store` directly against that storage. A stricter follow-up proof may also delete the fresh zero-fill itself: if the first ownership touch is a full-width dominating store before any read, the backend skips the `zeroinitializer` store and lets the first write define the entire cell. Treat this as a strict proof-backed lane, not a heuristic: if the trace stops being fresh, single-cell, non-escaping, or write-before-read, the lowering must fall back to the helper-owned or imported runtime paths.

### Filesystem Flow

`Kain fs_* calls -> kain-core runtime globals -> kain-fs portable crate -> stdlib wrappers -> runtime/native C facade -> LLVM/direct-C executables`

Interpreter-side file APIs delegate to `crates/kain-fs`, so strict globals can raise typed `FsError` values and `fs_try_*` globals can return structured result values. FS v2 also adds a runtime `FsSandbox` in `crates/kain-core/src/runtime.rs` for capability checks, host-path gating, and `fs://` mount resolution. New scoped helpers such as ranged reads/writes, streaming chunks/copies, watchers, and transactions resolve through that sandbox before touching the host filesystem. Watcher and transaction handles are process-local runtime registries owned by `kain-core`; the reusable semantics live in `crates/kain-fs/src/watch.rs` and `crates/kain-fs/src/transaction.rs`.

Native LLVM/direct-C builds load `stdlib/fs.kn`, which wraps the C facade in `runtime/native/src/core/stdlib_abi.c`. The current native parity surface includes ranged text reads, byte helpers encoded as lowercase hex, metadata encoded as key-value text, newline-delimited directory/walk path listings, and streaming copy. Keep the Rust and C lanes behaviorally aligned: `fs_hash_file` is SHA-256 in both lanes, deterministic walk/list order should remain stable, and new native-callable `fs_*` globals need precise `StdLib::new` return types so LLVM call lowering does not infer the wrong ABI. The encoded native helpers are a compatibility ABI, not a replacement for typed Kain records once native arrays/records/results are stronger.

Build and workspace orchestration also consume `kain-fs` now. Blade discovery/build, Fabric manifest/report IO, `kain check`, `kain test`, Omni staging, C/Rust FFI generation, import file discovery, and the trusted-local `kain-codebase` workspace helpers should use `crates/kain-fs` for reads, writes, deterministic directory entries, atomic artifact/report writes, copying, moving, removing, canonicalization, and SHA-256 hashing. Raw `std::fs` is still acceptable inside `crates/kain-fs` itself, native/runtime ABI adapters that must own OS handles directly, UE/vendor/demo surfaces, or narrow low-level process/file-handle code; do not reintroduce lane-local filesystem wrappers in the core build/import/FFI/workspace stack.

### Input Flow

`Raw host events -> target adapter -> kain-input event/session model -> stdlib/input.kn -> Kain source queries frames/actions/axes/text/trace`

`crates/kain-input` is the semantic owner. It reduces typed source events into `InputFrame` snapshots with semantic action pressed/down/released sets, frame-local axes, text commits, source provenance, and replayable traces. Source kinds are stable strings such as `human.keyboard`, `human.pointer`, `cli.stdin`, `ui.runtime`, `agent.intent`, `test.synthetic`, and `native.platform` so agents and runtime adapters can describe input without hardcoding target APIs into app code.

Interpreter execution registers `kain_input_*` bridge builtins in `crates/kain-core/src/runtime.rs` and root `stdlib/input.kn` exposes the public `input_*` helpers. LLVM/direct-C native builds now use that same root `stdlib/input.kn`, which wraps `runtime/native/include/input_system.h` and `runtime/native/src/core/input_system.c`. Keep adapters thin: Win32, web DOM, UE5 Enhanced Input, UI runtime, CLI stdin, and agent tooling should translate into this model instead of defining separate app-facing input systems.

### LLVM Native Actor ABI

`crates/kain-sys-codegen` now lowers actors against the canonical native runtime actor header instead of the legacy `KAIN_spawn` / `mq_*` lane.

- LLVM actor entrypoints use the canonical `(actor_id, mailbox, user_data)` signature and talk to `kain_actor_spawn_config_init`, `kain_actor_spawn`, `kain_actor_send`, and `kain_actor_receive`.
- The LLVM actor message and spawn-config layouts are emitted as explicit ABI types, so any change to `runtime/native/include/actor.h` must be reflected in codegen, `crates/kain-actor/src/native.rs`, and fixture validation together. `crates/kain-sys-codegen` depends directly on `kain-actor` for actor ABI sizing where possible.
- Native LLVM ask/reply now has a dedicated reply-port fast path instead of routing the return leg through the generic mailbox queue. The canonical handle shape is no longer a raw actor id in LLVM actor state; it is a first-class `KainActorRef = { actor_id, generation, execution_class, locality_class }`. `ask` / `ask_timeout` allocate a TLS-cached synthetic reply-port ref, handlers sending `reply_to.Reply(...)` lower to `kain_actor_reply_port_send_ref(...)`, typed waits use `kain_actor_reply_port_wait(...)`, and scalar `i64` waits keep `kain_actor_reply_port_wait_i64(...)`. The reply-port runtime no longer spawns a useless waiting OS thread; each successful ask rebinds a fresh synthetic actor generation so stale late replies are rejected on the next roundtrip. If actor roundtrips regress, inspect the actor-ref / reply-port seam before chasing mailbox micro-optimizations.
- Actor state ownership in the LLVM lane follows the native runtime contract: compiler-owned actor state is passed as `user_data` with `retain_user_data = 1`, while host/C/C++ callers default to borrowed `user_data` with no retain/release. Do not reintroduce unconditional `rc_retain` on actor `user_data`.
- Native actor ABI compatibility is queryable at runtime through `KainActorAbiDescriptor`, `kain_actor_abi_descriptor`, and `kain_actor_abi_descriptor_is_compatible`.
- `runtime/conformance/actor_runtime/run_tests.sh` is the broad native actor C conformance runner. It includes `test_actor_abi_contract.c`, which catches ABI drift, mailbox payload-size retention, user-data ownership mistakes, monitor tags, supervision snapshots, links, registry behavior, and scheduler statistics.

### Actor Crate Flow

`crates/kain-actor` is the shared actor-system model crate. It is intentionally independent from `kain-core` AST types so future native schedulers, LLVM lowering, C ABI glue, IDE tooling, and stdlib helpers can reuse the same vocabulary without importing the whole compiler frontend.

Current flow:

`Kain actor AST in kain-core -> typechecker resolves state/handler/method types -> TypedActor.actor_contract: kain_actor::ActorDefinition -> runtime-contract reflection and interpreter/runtime actor IDs/messages consume kain-actor primitives`

Keep new actor-system capabilities in focused `kain-actor/src/*.rs` modules, not in `kain-actor/src/lib.rs` and not as more hidden structs in `kain-core/src/runtime.rs`. `kain-core` should continue to own parsing, AST, typechecking, and interpreter execution; `kain-actor` should own reusable actor-system contracts, validation, mailbox/scheduler/supervision policy, behavior contracts, registry/address model, and native ABI descriptors.

### Formatting flow

`Kain source -> kain-core lexer/parser -> compiler-owned AST printer -> kain-driver helper -> cli format command`

The formatter now lives in `crates/kain-core/src/formatter.rs` and is intentionally compiler-owned. The rule is the same as the rest of the toolchain: editors, CLIs, and future LLM workflows should reuse the compiler printer instead of growing lane-local pretty-printers that drift from the actual grammar.

### Checking and source test flow

`Kain source tree -> kain-check discovery/frontend validation -> kain-test directive runner/runtime test/proof lanes -> cli check/test summaries and JSON reports`

`crates/kain-check` is the reusable typecheck-only pipeline. It discovers `.kn` / `.ks` files, skips build/generated folders, validates through `kain-driver::DriverSession`, and reports typed item counts, typed test counts, required runtime capabilities, and frontend errors without emitting backend artifacts.

`crates/kain-test` is the Rust-inspired compiletest-style harness plus the seed of Kain's solver-backed native test pipeline. It parses `//@` and `#@` directives such as `check-pass`, `check-fail`, `run-pass`, `run-fail`, `kain-test`, `prove-pass`, `prove-sat`, `target`, `error`, `proof-expect`, `smt2`, `ignore`, `skip`, and `known-bug`. Proof modes invoke Z3 from `PATH` or `KAIN_Z3` and record solver evidence in JSON reports. It should own future snapshot, revision, bless/update, compiler-extracted proof obligations, and target-conditional behavior rather than letting one-off scripts duplicate suite semantics.

The runtime test lane now recursively executes `test` items nested inside typed modules. `kain test` reports skipped cases separately from failed cases, and `--ignored` reruns ignored cases when the operator wants to burn down known-bug inventory.

`stdlib/test.kn` is the authored `std::test` surface for Kain-side outcome values. Keep author-facing test vocabulary there, while `crates/kain-test` owns suite discovery, directive execution, and solver/runtime reporting.

### Host bridge flow

`.kn source -> compiler/runtime contracts -> host bridge crates (Python, Node, C ABI, Rust crate FFI, codebase control) -> shared payload contracts via kain-interop`

Bridges exist to expose external capabilities cleanly. They should not become the default place to hide logic that Kain can already express and execute itself. Prefer Kain-owned logic for domain behavior, control flow, state transitions, and semantic contracts; use bridge crates for foreign APIs, packaged dependencies, and target-native runtime services.

`kain-codebase` is the trusted-local workspace authority layer, not a read-only indexer. Its default mode is `trusted-local`, which is allowed to mutate files and run toolchains for private/dev work. Future public or user-authored plugin policies should be host-side reviewed/curated modes layered above this crate, not fake safety inside the core local bridge.

The CLI exposes the same layer through `kain codebase inspect <path> --json` and `kain codebase run <cwd> -- <command> ...`. The run command is a structured capture operator: the Kain process succeeds when it captured stdout/stderr/status correctly, and callers must inspect the child `success`/`status` fields.

Current native-ui packaging rule for C ABI imports:

- `kain-c-ffi` now routes C type classification through `kain-foreign-abi`. The v2 bridge can represent callback typedef parameters, inline callback pointers, multi-level pointers, raw scalar pointers, arrays-as-pointers, and byte-buffer pointer returns as explicit `Any`-surface handles instead of rejecting them during extraction. By-value aggregates are captured in the ABI graph but still gated from callable lowering until layout metadata is known.
- `kain-c-ffi` is no longer only an `Interpret`/`Test` lane concern. The Rust/native-ui packaging lane now emits packaged bridge manifests, copies bridge/shared-library sidecars into the app artifact set, and has the generated native app launcher load those packaged bridges before boot.
- This does not mean the current native UI host is a full general-purpose Kain interpreter. The lane is still bundle-driven; the packaging change makes foreign bridge dependencies explicit and shippable rather than hidden behind cache-local host-backed behavior.

### Blade workspace flow

`workspace root -> blade crate discovers blade roots -> kain-build plans a typed task DAG -> CLI, Fabric, filesystem modules, Rust crate FFI, C ABI FFI, Cargo, GPU, Node/Bun, and reports consume the same blade metadata`

The blade system is intentionally local-first and crate-like. A `KAIN.toml` can declare `[blade]` metadata and optional `rust`, `cffi`, `fabric`, and `gpu` sections, while a plain `Cargo.toml` under `crates/*`, `apps/*`, or `blades/*` is still exposed as a synthetic Rust blade. This makes a Kain blade able to live beside Rust crates, and a Rust crate able to be equipped from blade-aware workflows without duplicating path rules.

`kain equip <blade>` is the human-facing resolver. `kain blades list`, `kain blades graph`, and `kain blades check` are the inspection and validation surface. `kain blades build .` and the standalone `blade build .` command are the build surface; `kain blades run [blade]` and `blade run [blade]` are the immediate execution surface through `kain-run`. Runtime code should call the `blade` crate, `kain-build`, or `kain-run` instead of re-scanning folders directly; future remote update/install work should extend these crate boundaries rather than inventing a second registry path.

Blade module resolution now merges module roots from ancestor workspaces as it walks upward from the current directory. That means a runnable blade launched from `blades/<name>/src` can still import sibling blades declared by the repo-root workspace instead of only seeing its own local blade root.

Build artifacts are deliberately workspace-local and disposable:

- `.kain/out/<host>/<lane>/<target>/<unit>/<task>/...` owns canonical build products, including Kain file/project/native-ui outputs, C sidecars, Cargo target dirs, GPU bundles, and per-task `kain-artifacts.json` manifests.
- `.kain/cache/build/stamps/*.stamp` owns task fingerprints over inputs, adapter settings, outputs, profile, and target.
- `.kain/reports/build/session-*.json` plus `.jsonl` owns build reports and event streams.

`[build]` in root or blade `KAIN.toml` can override `artifact_root`, `cache_root`, and `profile`, while CLI `--lane bootstrap|dev|release|dist|selfhost` chooses the invalidation lane. `build.kn` is the preferred live authority for explicit DAG work: `build_check(...)`, `test_suite(...)`, `proof_obligation(...)`, `bench_case(...)`, `attrition_case(...)`, `native_executable(...)`, and `certify_gate(...)` add build, proof, benchmark, attrition, executable, and certificate tasks with inputs, outputs, dependency requirements, matrix axes, telemetry channels, and host capability gates. Legacy `build_task(...).kind(...)` remains accepted. `KAIN.toml` remains the compatibility lane for metadata not yet promoted into script authority, especially C-FFI library declarations.


The important rule is: the mirror lane proves reference and repair behavior, while the owned lane proves real selfhost direction. Keep the Rust mirror lane available for comparison, but promote the manifest-first hand-written lane as the compiler that is supposed to survive once bootstrap is over.


The architecture rule here is the same as the viewport and compute lanes: shader-canvas execution can optimize presentation, but it must stay subordinate to compiler-owned bundle truth rather than inventing a renderer-local UI shader dialect.
